# Native Materials Slice 3 Implementation Plan — G9 Overview Clipping Gate

**Status:** draft, revision 2 (post-review), not yet executed.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the G9 gate: prove `CropRenderElement` over niri's pixel-shader
elements renders retained pixels correctly, and replace the monitor's HACK
crop bounds with bounds derived from the workspaces actually rendered, so the
inflated glass slab renders correctly through overview and workspace
switches.

**Architecture:** Two changes plus evidence. (1) A deterministic
characterization run establishes what the 2024-era HACK comment still means
today: niri's shaders have since moved to CPU-side `input_to_geo` matrices
over `niri_v_coords`, and code analysis says that path survives cropping (the
crop wrapper hands `draw()` a consistent `(src, dest)` pair and `tex_matrix`
keeps `niri_v_coords` in fraction-of-full-element space). A force-crop
instrument build renders a static scene with the band crop on vs. off;
byte-identical frames retire the coordinate-space claim with evidence.
(2) `Monitor::render_workspaces` crop bounds become per-workspace and derived
from the **rendered** workspace list: a side is cropped exactly when another
rendered workspace joins it there; overview keeps its both-sides card band;
idle stays unbounded. The visible payoff is confined to strip-end void
boundaries (spring overshoot / rubber-band past the first workspace — see
Findings); joins keep their clean hard cut, which this plan treats as
correct-by-design and records as such. The `niri_size` uniform mismatch found
during analysis is **documented and deferred** (no shader reads it; no
consumer, no fix — YAGNI). The damage-tracking note about maximized GTK
windows is retained verbatim in the rewritten comment and recorded as
not-exercised; this slice only ever crops less than today, so it cannot
regress that bug.

**Tech Stack:** Rust, niri v26.04 (Smithay 0.7.0 rev `ff5fa7df`), GLES2,
nested-winit live verification via the slice-2 replay harness, Tracy for the
performance record, ImageMagick for image comparison.

**Spec:** `docs/materials/2026-08-22-v1-design.md` §5 "Slice 3 — overview
correctness gate" and §6 Verification, informed by
`niri-experiments/docs/research/2026-08-22-gap-analysis.md` §G9. The defect
site is the HACK comment at `src/layout/monitor.rs:1683-1703`.

## Findings this plan is built on (verified 2026-08-24, rev 2)

- `ShaderRenderElement::src()` and `MaterialRenderElement::src()` both return
  the unit rect; `CropRenderElement::from_element` (smithay
  `elements.rs:145-194`) computes a sub-`src` equal to the retained fraction
  and a `geometry()` equal to the intersection. `RescaleRenderElement` and
  `RelocateRenderElement` pass `src` through untouched. So at
  `ShaderRenderElement::draw`, `(src, dest)` is always a consistent pair and
  the vertex shader's `niri_v_coords = tex_matrix * position` stays in
  fraction-of-full-element space under any `Crop → Rescale → Relocate` stack.
- Every current fragment shader (border, shadow, resize/open/close preludes,
  material) consumes `niri_v_coords` plus CPU-computed matrices or
  element-UV uniform rects. `niri_size` is declared in six shaders but read
  by **none**, while `draw()` sets it to the cropped `dest.size` — wrong
  under crop, but latent. **Deferred:** no consumer means no fix in this
  slice; the mismatch is recorded in the results doc so a future consumer
  (the material shader is the obvious candidate) fixes the uniform first.
  The HACK comment predates the matrix refactor (Feb 2024, upstream
  `340bac06`).
- Current crop policy in `Monitor::render_workspaces` (monitor.rs:1693-1703):
  fully unbounded when idle; a horizontally-infinite vertical band
  `[0, height]` for **every** workspace whenever a workspace switch **or**
  overview is active.
- **Visibility geometry** (`workspaces_render_geo`, monitor.rs:1474-1503):
  workspace bands form one contiguous, index-ordered vertical strip (gap only
  under overview zoom). Therefore, during a plain switch, every band
  boundary strictly inside the viewport is a **join between two rendered
  workspaces** — except past the strip's ends, where the boundary faces
  void. Cropping at joins is correct by design (windows themselves crop
  there; a workspace's slab must not overlay the neighboring workspace's
  content). Cropping an off-screen edge is invisible. So the only *visible*
  defect in the current band policy is at strip-end void boundaries: spring
  overshoot or rubber-band past the **first** workspace shows void above its
  band, and a slab lip crossing that top edge is cut against the void. (The
  bottom strip end cannot exhibit this: niri's empty-last-workspace
  invariant means the last band with content always has an empty workspace
  below it, and an empty workspace has nothing to clip.) The slice-2
  recorded "G9 vertical-lip clipping ... at the workspace boundary"
  (`niri-experiments` commit `a27eb8f`) is re-examined by Task 1 under this
  lens: a clean cut at a join is correct behavior, to be reclassified as
  such in the results doc; a cut at a void boundary, or any displaced/
  glitched retained pixels, is the defect.
- The other `CropRenderElement` site (`scale_relocate_crop`, niri.rs:6483)
  crops layer surfaces and solid colors in the overview, never tile/material
  elements — out of scope.
- Horizontal bounds stay infinite **by design**, not by hack: the overview
  intentionally shows scrolling-layout content overhanging workspaces
  horizontally.

```rust
/// Crop bounds for one workspace's render elements, in workspace-local
/// physical coordinates.
///
/// Cropping exists to keep a workspace's elements from overflowing into a
/// neighboring workspace, so each side is cropped exactly when another
/// **rendered** workspace joins it there: in the overview every workspace
/// is a card with neighbors on both sides; during a plain workspace switch
/// the first and last rendered workspaces have an open outer side, which
/// keeps decorations that extend past the strip's ends (shadows,
/// decoration shaders) from being cut against the void during spring
/// overshoot. With no switch or overview nothing can overflow into view,
/// and the bounds are effectively infinite. Horizontal bounds are always
/// unbounded: scrolling-layout content intentionally overhangs workspaces
/// horizontally (visible in the overview), and the output edge clips
/// everything else.
///
/// `rendered_pos`/`rendered_count` describe the workspace's position in
/// the y-ordered list of workspaces actually rendered this frame, not the
/// monitor's whole workspace strip.
fn workspace_crop_bounds(
    height: i32,
    overview_active: bool,
    switch_active: bool,
    rendered_pos: usize,
    rendered_count: usize,
) -> Rectangle<i32, Physical> {
    let joins_above = rendered_pos > 0;
    let joins_below = rendered_pos + 1 < rendered_count;

    let (top, bottom) = if overview_active {
        (0, height)
    } else if switch_active {
        (
            if joins_above { 0 } else { -i32::MAX / 2 },
            if joins_below { height } else { i32::MAX / 2 },
        )
    } else {
        (-i32::MAX / 2, i32::MAX / 2)
    };

    Rectangle::new(
        Point::from((-i32::MAX / 2, top)),
        Size::from((i32::MAX, bottom - top)),
    )
}
```
